# 64. A release carries its merged policy, and it is enforced while work runs

Status: accepted, 2026-11-15. Extends ADR 0024 (effect tools and permits per call), ADR 0035 (engine isolation) and ADR 0046 (step timeouts). Weakens nothing in them.

A `Policy` document was checked when a release compiled and then forgotten: the merge ran only for two or more policies and its result was thrown away, so nothing at run time read an allowed or denied operation, a maximum runtime, a minimum isolation, separation of duties or production approval. A policy that is not read is a comment, not a safeguard.

## Decision
1. **The merge is the release's effective policy.** The compiler merges every `Policy` document (one is enough) in document order, restrictively (allow-lists intersect, deny-lists union, caps take the minimum, isolation and separation of duties only tighten; a broadening or null-disable layer still rejects the release). The result is stored in the manifest as `effectivePolicy`: the layers, the effective values, the layer that decided each field, the layer that first denied each operation and each layer's own allow-list. It is part of the manifest, so the release digest pins it, and the release view shows it. A release with no `Policy` document stores `null`; nothing is invented for it (no 120 s floor).
2. **An empty allow-list states no allow-list.** `allowedOperations: []` in a layer restricts nothing. Two non-empty lists that share nothing leave an allow-list of nothing (`[]` in the effective policy, `null` when no layer wrote a list), and refuse every operation.
3. **An operation is a tool id.** A step performs the tool of a tool step, every tool its agent lists, or the tool of its evaluator. At admission a step with an operation the policy denies, or its allow-list leaves out, is refused: the job is recorded as `failed` with the refusal (so its run page can say why), no runner sees it, the step and the run fail, and the refusal names the layer and field (`Policy config/x.yaml denies the operation fixture.echo (deniedOperations)`). An effect proposal is checked the same way before an approval is asked for.
4. **The maximum runtime only cuts down.** An attempt's deadline is the step's `timeoutSeconds` or the policy's `maxRuntimeSeconds`, whichever is shorter; a step that declares none gets the cap. The timeout message names the layer when the cap is what ended the attempt. A held change (an act job) is capped too. The job's queue deadline is untouched.
5. **Isolation is an ordered level.** `trusted-local` < `ephemeral-container` < `dedicated-vm`. A runner or engine states the level it provides; it takes a step when that level is at least what the step needs. The job's placement is raised to the policy's minimum at admission, so a statement below the minimum is never offered the job, and the runner picks an engine by the same order. A name outside the order matches only itself. (ADR 0035's "equality" was interim, as it said.)
6. **Approval time: one named hook.** `approvalPolicyProblem(subject, approver)` runs in `approval.decision`, before step-up, and again in `admitApprovalDecision` before the human-session check so a machine principal is told which policy refused it. It reads the policy of the release the subject is pinned to and of the organization's active release; the stricter holds. `productionHumanApproval` (always `required`): a change whose target environment is `production` or `prod` (alone or with a `-`, `_`, `.` or `:` suffix) is decided by a person, not a machine principal. `separationOfDuties`: the approver is not the person who started the run the approval came from, nor the owner of the mission it serves. The always-on rule (the requester never approves their own request) is unchanged. Rejecting is never restricted.

## Consequences
- The starter's `operations-policy` now lists every tool of the starter (and the three CV tools) as allowed, and caps an attempt at 3600 s (its longest declared step is 900 s). Its lists named two evaluator tools only and were never read; read as written they would have refused the starter's own agents. The type and workspace documents were re-pinned to the new policy digest.
- Separation of duties is on in the shipped policies, so a workspace owner can no longer approve an effect of a mission they own or a run they started: a second approver is needed. This reverses the comment in `effects.ts` that let the owner decide their own mission's call; it is the policy field doing what it says. A policy that states `separationOfDuties: false` in its single layer turns it off.
- The environment of a change is the first `allowedEnvironments` entry of its Tool document; no shipped tool is `production` yet.
- Risk tiers build on this hook rather than adding another.

## Limits
- `maxMicroUsd` is stored and shown, not enforced here (agents carry their own `maxMicroUsd`; ADR 0008).
- Runners can state `ephemeral-container` (tools) or an engine's own level; none states `dedicated-vm` yet, so a policy that asks for it places nothing until one does.
