# 78. The audit log is a hash chain with signed checkpoints

Status: accepted, 2026-11-16.

Events were append-only by convention, each with a digest of its own payload (ADR 0032 gave each an actor). Nothing made a change to them visible: someone with write access to the data files could edit, remove or reorder an event and nothing would say so. `audit_checkpoints` existed with no writer. The audit trail is only evidence if tampering shows.

## Decision
1. **A chain per log.** Each event log is its own chain: the control log of each organization, and each workspace database. Every event stores its position (`chain_seq`, dense from 1), the digest of the event before it (`prev_digest`) and its own `chain_digest`, a domain-separated hash of the previous digest, the position and every column the event records (ids, aggregate, type, payload digest, time, and the actor: id, kind, attempt, acting-for). The first event continues from a genesis digest bound to the organization and the log, so a chain cannot be moved under another scope. The position and the insert happen in one transaction inside `Store.emit`, so two events never share a position and a rolled-back caller leaves no gap.
2. **One definition, in `packages/contracts/src/audit-chain.ts`.** The digest functions, the signing bytes and the verifier live there and are used by the Governor to write, by its own self-check and by `brain audit verify`. The verifier is pure (no database, clock or network), walks every row in written order and reports the first break and where: an event with no chain position (added outside Brain), a position that is not the next one (removed, added or moved), a link that does not continue the event before, a payload that no longer matches its digest, any other edited column, and a checkpoint that is unsigned, signed by an unknown key, disagrees with the log at its position, or lies beyond its end. It recomputes the payload digest from the stored payload instead of trusting the stored digest. A plug-in list of per-event checks runs on events whose position is sound; the run-receipt check (decision 8) is always the first of them.
3. **Signed checkpoints.** A checkpoint is the log, a position, the head digest at that position, the time and the key id, signed with the Governor's audit key (ed25519, `node:crypto`). They are written by a pass under `system:audit` when `BRAIN_AUDIT_CHECKPOINT_EVENTS` (1000) events or `BRAIN_AUDIT_CHECKPOINT_MINUTES` (15) minutes have passed and something is new, and on demand (`POST /v1/audit/checkpoints`, `brain audit checkpoint`). They are stored in the control database for every log, including workspace logs, so a checkpoint is never in the file it vouches for. A checkpoint is only signed over a log that has just been verified up to its head, and writing one is not an event (it would move the head it signs). A repeat request with nothing new returns the existing checkpoint.
4. **The key.** An ed25519 key is generated at first start; its private half is a file in `<data dir>/audit/<key id>.key` (mode 0600, created exclusively, checked on every use) and never leaves the host; the public half is in `audit_keys`, returned by `GET /v1/audit` and in the diagnostics bundle. The key id is derived from the public key. **Rotation** (`POST /v1/audit/keys/rotate`, `brain audit rotate-key`, an administrator, with step-up when a factor is configured) signs a last checkpoint of every log with the old key, makes a new key, signs a hand-over (previous id, new id, new public key) with the old key, deletes the old private file, and records the new key in each organization's chain as an `audit.keyRecorded` event attributed to the person who rotated. Retired public keys stay, so older checkpoints stay verifiable. A key whose file is lost is replaced by a rotation with no hand-over.
5. **Keys are believed only as far as they are anchored.** Without a pin, the verifier takes the export's keys, requires each key id to be derived from its public key and to equal what the chain recorded under that id, and requires every recorded rotation to carry a valid hand-over. With a pin (`--trust-key <file>`, for example the keys saved from an earlier export) only pinned keys and keys reached from them by hand-over are believed. The result states which of the two was used.
6. **Self-verification.** The same pass walks every log in slices (`BRAIN_AUDIT_SCAN_PAGE`, 20000 events per pass) under `system:audit`, keeps the running verifier alive so new events are checked as they arrive, re-reads the newest events each pass, checks the head against what it verified, and restarts the whole walk every `BRAIN_AUDIT_RESCAN_MINUTES` (60). Its result is the `audit` probe on Health ("Audit log verified: N events in M logs. Last checkpoint 5 minutes ago."): unavailable with the break named when verification fails or the signing key is missing, degraded when checkpoints are overdue; a failing probe alerts the workspace owners once, like every other probe.
7. **Export and CLI.** `GET /v1/audit/export?scope=control|workspace:<id>&afterCursor&limit` pages a log in written order with its checkpoints and the keys (organization administrators). `brain audit export` assembles an export file; `brain audit verify` fetches (or reads `--file`) and verifies locally, exiting 1 and naming the break. The CLI is an HTTP client only.

8. **Signed run receipts.** When an attempt ends the runner states, in one **run receipt**, what the attempt was and did: attempt, job, fence, runner and epoch, workflow run and step, configuration and execution digests, the key id, engine id, version (its adapter digest) and model route, start and end, outcome, the engine's final usage totals, the digest of the evidence bundle it is about to submit (null when it submits none) and the digests of its artifacts. It signs the canonical JSON (RFC 8785, prefixed `brain:run-receipt:v1`) with the ed25519 key it enrolled with. The definition, the signing bytes and the check are in `packages/contracts/src/run-receipt.ts`, used by the runner to sign, the Governor to verify and the offline verifier. A completion without a signed receipt is refused (`RECEIPT_UNSIGNED`); the current build always signs and there is no unsigned path. The Governor also refuses a receipt whose attempt, fence, runner, run, step, configuration or execution is not what it holds, whose outcome is not the result reported, whose key is not an unrevoked key of that runner (`RECEIPT_KEY_UNKNOWN`, `RECEIPT_KEY_REVOKED`) or whose signature does not verify. The receipt and signature are stored as sent in `attempt_receipts` (updates and deletes abort) in the completion's own transaction, and written to the control chain as an `attempt.receipted` event of the attempt. The runner builds its evidence bundle before completing so that the digest it signs is the bundle it submits; the Governor refuses a bundle whose digest is not the one the receipt names. `evidence.get` returns the stored receipt with the signature checked again, and the run's Evidence tab shows "Signed by runner <id> (verified)" with the receipt digest.
9. **Runner keys in the chain.** Enrollment now keeps every public key a runner enrolled with (`runner_keys`, the key id derived from the key) and records it as a `runner.keyEnrolled` event; `runner.rotated` and `runner.deregistered` list the keys they end (`revokedKeyIds`). Quarantine does not end a key (it is reversible and revokes the runner's sessions). `brain audit verify` (and the Governor's own scan) judges each `attempt.receipted` event against what the control chain says at its position: the key was enrolled, by that runner, was not yet ended, signed exactly this receipt, and the event is the receipt of the attempt it is filed under, once. The first receipt that fails is reported with its attempt and why. A receipt signed before its key ended stays valid; one signed after is refused, live and offline.

## Consequences
- **What it does not prove.** Someone who can rewrite the database and the signing key file can rebuild a chain and sign it: the key is on the same host. An export held elsewhere, and a pinned public key, are what make that visible. Events after the last checkpoint of a log are protected by the chain only: a cut tail there cannot be told from a log that never had those events, so checkpoints are frequent for that reason. Events written before this change (none in a fresh install) have no chain position and would be reported.
- A mid-log edit of an event already passed by the live walk is found at its next full walk (at most an hour by default), or at once by `brain audit verify`.
- Cost: one indexed head lookup and one hash per event, in the transaction that already existed.
- **What a receipt does not prove.** That the runner told the truth: the signature binds the statement to the runner's key, and a compromised runner can sign false statements, which the evaluator and the checks exist to catch. It also does not say the receipt was made at the time it says: the Governor's own record of when it was accepted is the chain event. A receipt whose evidence digest is null does not vouch for a bundle later submitted for the same attempt (a bundle it does name is checked).
