# 26. Single sign-on with the company directory provisions people by default role or group claim

Status: accepted, 2026-11-13. Builds on `docs/implementation/24-native-identity.md`: password, authenticator and passkey sign-in stay.

## Decision
1. **OpenID Connect, authorization code with PKCE (S256), state and nonce**, through the pinned sign-in vendor's generic provider. The ID token is verified (signature against the directory's JWKS, issuer, audience, nonce) before any claim is read. Sessions are the vendor's, so every existing check (revocation, membership, step-up binding) applies unchanged.
2. **It is Administration configuration, not an environment variable.** `identity.oidc.set` (scope `identity:security`) stores issuer, client id, a **secret reference**, and the provisioning rules in `control.db`; `identity.oidc.get` shows them. The secret is only ever named, resolved when the provider is registered and never stored, returned, logged or put in an event: `file:/abs/path` (an owner-only regular file inside `<data>/secrets/` or `/run/secrets`) or `env:BRAIN_OIDC_<NAME>`. Both are restricted because the secret is sent to the issuer's token endpoint: a setting must not be able to name the Governor's keys or any other variable. A setting that cannot resolve its secret is refused while enabled. The provider is registered after the command commits, so no restart is needed; rotating the secret means saving the setting again. One provider per Governor, owned by one organization.
3. **First sign-in may create the person**, only when `autoProvision` is on. They get the workspace roles of the groups they assert (claim name configurable, dotted paths allowed, mapping `group` to `viewer`, `operator`, `workspace-lead` or `approver`), else the default role, in the configured workspaces (all active ones when none are named). No default role and no matching group: refused **before any account exists**, as are an unverified email and a domain outside the allow-list. SSO never grants organization roles; administrators stay a deliberate grant.
4. **An existing member signs in to the same account** (verified local email), keeping their principal and roles. A returning or linking identity must already be a member of the organization that owns the setting; otherwise it is refused, so one organization's directory can never sign in as another organization's member. Roles are set at first sign-in only: a later sign-in never rewrites what an administrator changed. Suspending the principal ends the session's authority at once, as for any member.
5. **A directory-only person enrolls an authenticator without a password**, only right after a directory sign-in (5 minutes) and only for an account that came from the directory; reading, regenerating, removing or re-enrolling it needs a password, which they lack, so a stolen session cannot swap the factor that guards approvals. They then approve effects like anyone else (the requester is still never the approver).

## Not decided here
Group-driven de-provisioning (a person removed from the directory keeps their Brain account until suspended; the session lifetime is 12 hours), SAML, and several providers per Governor. A real directory tenant has not been tested (backlog); the flow is tested against a local fake provider.
