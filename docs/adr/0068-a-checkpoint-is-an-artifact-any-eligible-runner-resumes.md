# 68. A checkpoint is an artifact any eligible runner resumes

Status: accepted, 2026-11-15. Supersedes points 1, 2 and 4 of ADR 0045 and the first limit it lists; the rest of 0045 stands (the engine starts from the checkpoint and never reopens it, a resume takes a stopped task over). Builds on ADR 0006 and ADR 0030.

ADR 0045 left the saved conversation on the disk of the runner that took it and pinned the resumed step to that runner, so a runner that was gone, wiped or past its newest 50 could not be resumed.

## Decision
1. **The runner uploads the conversation; the Governor keeps it.** When an attempt of an engine that offers `checkpoint` does not succeed, the engine hands its saved conversation to the runner, which uploads it as an artifact of that attempt (media type `application/x-ndjson`, classification `internal`) through the ordinary attempt artifact route, before it completes. Size limit, classification and retention are those of every attempt artifact: the content-addressed store, referenced from the association so it is never swept, never an event and never evidence. A conversation that cannot be uploaded (over the 8 MiB limit, or the lease is gone) leaves no checkpoint rather than one nobody can use.
2. **The checkpoint names the artifact it was uploaded as.** The Governor records a checkpoint's engine state only when it is an artifact this attempt uploaded, in this workspace, with the digest and size the runner reports; anything else records no checkpoint. The digest on the checkpoint is the artifact's.
3. **Resume pins no runner.** `session.resume {sessionId}` still starts a new run of the source run's workflow and input and a new session (new fence, new attempt) with `resumedFrom`, which now names the source session and the checkpoint digest only. The continuing step's job asks for the engine and its `resume` feature and is claimed by any runner the claim rules admit: runner group, host-tool group, isolation, capabilities, engine and engine isolation, capacity. The claim and the offer ask one function for that.
4. **The claiming runner downloads and verifies.** The runner fetches the checkpoint from `GET /runner/v1/attempts/{id}/checkpoint`, which names nothing: the Governor serves the artifact its own job payload pins, to the runner holding that live attempt only. The runner checks digest and size, and the engine checks them again when it stages the bytes (`stageCheckpoint`); a copy that differs is refused, with the reason, before any session starts and the attempt fails with it.
5. **Offered when it can work.** `session.get` carries `continuation.resume` with `possible` true when the checkpoint artifact is still stored and verifies, some registered runner would be admitted for the step with the engine's resume (capacity is not judged: a busy runner frees up) and the task takes a new run. Otherwise it says why in plain words (no runner is registered, none is online and taking work, none offers resume for the engine, or those that do miss what the step needs), and says nothing when there is no checkpoint. The command re-checks the same facts and refuses with the same sentence. The console then offers the existing fresh start.

## Limits
- Only Pi saves and resumes today; ACP, Claude and the fixture engine offer neither.
- A conversation over 8 MiB is not shared and so not resumable.
- The saved conversation can hold anything the agent saw; it has the classification and reach of the attempt's other artifacts and no more.
