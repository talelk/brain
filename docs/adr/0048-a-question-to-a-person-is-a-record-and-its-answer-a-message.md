# 48. A question to a person is a record, and its answer is a message

Status: accepted, 2026-11-15. Builds on ADR 0005 and 0011 (attention items are derived and notify once under the per-mission throttle) and ADR 0042 (a Brain tool is one command run as the session principal).

A session that cannot go on without a person's input could only park its task or guess. It had no way to ask, and a person had no way to answer into the session.

## Decision
1. **A fifth Brain tool.** `mission.ask` is the Brain tool of command `mission.question.ask`, declared like the other four (class `read`, allowlisted on the task worker). It takes one `question` (at most 1000 characters). The mission, the team member, its attempt and its task come from the Governor with the credential, never from the model. Only a team member's session can run the command; a person cannot, and the session allowlist (ADR 0032) admits it by its place in the tool table.
2. **A question is a record, never a condition.** It is written once (a trigger refuses edit and delete) in `mission_questions`: mission, asking member, attempt, task, text, time. Nothing says whether it is open. It is open while no answer exists, and Needs you derives the blocking item `question` (tier 3, with plan proposals and parked work) from the two records, on missions not closed. The item names the member's role and carries the question as its detail, so the push body and the Needs you row say what is being asked.
3. **The answer is an ordinary mission message.** A person answers from the mission's composer, which sends `mission.message.send` with `answersQuestionId`. The Governor accepts that only from a person, for an unanswered question of the same mission, addressed to the member that asked, and never as a correction. The answer is stored on the message (`answers_question_id`, unique, so a question is answered once) and delivered as any message to that member: steered into a live session when its engine allows, otherwise read at its next session start, where it is labelled "A person's answer to your question" with the question quoted. It is a claim and authorizes nothing. A session cannot clear a person's item by sending a message that names the question.
4. **The asker is not held.** The tool returns at once and tells the model its answer arrives later as a message, not to ask again and to carry on; there is no blocking call and no wait that a lease or a budget would have to account for. If the member's task finishes before the answer, the message waits for its next session, as every message to a member does.
5. **Questions are rationed per session.** A session is one attempt. It may ask at most 3 questions in all, and a member may have at most 2 waiting at once, so a failing task that starts new attempts cannot start the count over and a session cannot flood the queue. Beyond either limit the call fails with the reason in plain words and an instruction to carry on. The notification pass keeps its per-mission window (ADR 0011), so a burst of questions on one mission is one push.
6. **Where the person is sent.** The item opens the mission's Live tab with the composer open on that question (`?question=<id>`), from Needs you, the bell and the push link alike; the Live tab also lists the mission's open questions, so they are seen without a notification.

## Limits
- The caps are constants (`MAX_QUESTIONS_PER_SESSION`, `MAX_OPEN_QUESTIONS_PER_MEMBER`), not settings.
- A question nobody answers stays in Needs you until the mission closes; it has no expiry, because the asking member may still need it.
- Only the member that asked receives the answer; other members see it only if the asker repeats it.
