# Load and capacity

Measured 2026-11-13 on a shared 14-core laptop (Node 24), in-process Governor core, loopback HTTP excluded; treat the numbers as noisy ceilings.

| Benchmark | Result |
|---|---|
| `pnpm bench` (starter org; 100 queries, 50 commands) | query p50 0.35 ms, p95 0.74 ms; command p50 5.7 ms, p95 9.5 ms; 277 MB |
| `pnpm bench:steady:quick` (25 workspaces, 50 runners, 100k jobs, 1000 pending approvals; 20 operations a second, bursts of 50; 3 x 60 s) | medians: query p95 52 ms, command p95 49 ms, 24 ops/s, 563 MB, no errors. The first trial is the cold one (query p95 about 180 ms) |

**Steady benchmark, before and after the row 96 fix** (`pnpm bench:steady:quick`, same machine, medians of 3 x 60 s plus the 10x-history trial): query p95 36.2 -> 12.7 ms, command p95 45.3 -> 29.1 ms, event-loop delay p99 92.6 -> 49.6 ms (budget 50), 10x-history query p95 86.3 -> 17.0 ms (budget 150). Causes (CPU profile, `EXPLAIN QUERY PLAN`): (1) `jobs.list` counted a workspace's runs with an index that lacked `organization_id`, so each count read one table row per run (6 ms at 4,000 runs per workspace, growing with history): `jobs_scope_state` now covers it (0.2 ms); (2) per-run lookups scanned (`jobs` by run id, `execution_links` and `task_drafts` by run id, `evidence_bundles` by the run id inside the manifest): indexed; (3) the open workspace-database cache held 16 handles for 25 active workspaces, so every operation reopened one and closed another (pragmas, identity and schema check): the default is now 64 (`BRAIN_MAX_WORKSPACE_DBS`, at most 256); (4) the once-a-minute replica snapshot ran SQLite's `integrity_check` on the Governor's thread, which froze every request for 1.2 s on a 175 MB data set: it now runs on a worker thread (worst stall 120 ms). The event-loop figure is a burst of synchronous commands, each with three durable commits (`synchronous=FULL`), so it sits near the budget on a loaded machine.

**Growth across trials.** The steady benchmark exits non-zero (`growthAcrossTrials`) when a later trial passes trial 1 by 1.5x (+10 ms event loop, +5 ms command) or 1.2x + 32 MB of RSS. Round 1 (2026-11-13): `autoStartPlan` prepared statements for every mission a workspace ever had (26 ms per command at 500 missions against 4.3); it now reads only missions with ready work. Round 2 (2026-11-14), the full 3 x 10 min run still failing on a quiet machine: event-loop p99 48 / 72 / 87 ms, command p95 24 / 30 / 42, query p95 22 / 32 / 48, RSS 657 to 720 MB. Causes: (1) `jobs.list` sorted all of a workspace's runs for each page (`jobs_scope_created` serves the order, one workspace at a time); (2) `sessions` was scanned per run (`sessions_job`); (3) every statement was compiled again on each call, about half of all CPU (each connection now keeps 256 compiled statements); (4) `attention.list` ran two lookups for every open mission and the Quality counts scanned every event (`events_type`; only missions with parked work or verifying are examined); `approvals_scope_expiry` serves approval pages. After, same protocol: p99 21 / 19 / 19 ms, command p95 16 / 7.5 / 7.7, query p95 3.6 / 3.7 / 3.7, RSS 351 to 379 MB, 10x-history query p95 6 ms, exit 0. Existing databases get the indexes from `scripts/repair-live-schema.ts`.

**Regression threshold.** `pnpm bench` now exits non-zero when query p95 passes 50 ms, command p95 passes 100 ms or memory passes 1 GB; the steady benchmark keeps its own budgets and exit code. Run `pnpm bench` before a release (`verify:release` does).

**Decision: keep SQLite, with the replica (ADR 0027), until the benchmark says otherwise.** The Phase 4 target is about 50 missions a week for three teams, which is far below one operation a second against a store that sustains 24 a second with command p95 under 50 ms. One writer, WAL, and a second-host copy cover it. Revisit when the steady benchmark's 1x medians pass their budgets, when sustained load approaches 20 operations a second in production metrics (`brain_queue_depth`, attempt duration), or when snapshots take long enough that replica lag stays degraded.

**Capacity.** Concurrent work is the slots of the online runners (Health, `runners`); a second runner host adds its slots (docs/howto/replica-and-second-runner.md). Queue depth and the age of the oldest queued job are in `/metrics`, with an alert at 30 minutes.
