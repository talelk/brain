# Runtime status and continuation — 2026-10-28

## Model qualification passed — 8 November

`scripts/run_model_qualification.ts` ran the six qualification cases three times each (18 runs) against `local-qwen/qwen3.8-flash-next-a5b` through OpenCode 2.2.5 — re-pinned from 2.1.4 after the native loader was checked against `opencode.json` — each run in a fresh git workspace outside the repository, from a separate git worktree so the checkout could not be touched; the checkout was byte-for-byte unchanged afterwards. All 18 passed against harness-side oracles: the tool server's own call log (Q01, Q02), git diff and a real `tsc` (Q03), test exit codes and an unchanged test digest (Q04), no attempted read of the planted secret and an unchanged policy file (Q05), and, for Q06, a compaction observed through OpenCode's session API followed by a server restart and the completed next action. Raw traces, tool logs and stderr are in `artifacts/runtime/QWEN/`. G01–G08 were rerun on the same commit; `runtime-readiness.json` records every gate and the qualification as passed. An earlier user-run attempt (3/18) was discarded as invalid: the runner declared MCP servers and permissions in the pre-2.2 format and the agent worked in the repository rather than its workspace; the runner now uses the 2.2.5 formats and aborts on any repository change. Qualification covers the OpenCode coding assistant on this model, not the Brain product's own features; independent release certification remains separate required evidence.

## G08 steady load: benchmarks and projection hot path — 8 November

The G08 steady benchmark still sent the removed `board.create` command, so every command was refused (about 5,000 errors per trial) and command latency was never measured because commands were not awaited. All benchmarks now send `mission.create`, and the steady benchmark awaits each command and counts refused receipts as errors. Measured honestly, applied commands were slow: each one projected the stream across every workspace — reopening workspace databases evicted from the 16-handle cache — and regrouped the whole `attempt_events` table. The projector now tails only workspaces whose event logs gained rows (the store marks them on `emit`), skips the attempt scan when the append-only `attempt_events` head has not moved, and sweeps every workspace from the maintenance tick and on a process's first pass. On a 15-second trial command p95 fell from 52 to 6 ms and event-loop p99 from 65 to 23 ms, within budget.

## Rejecting proposals and resolving parked work — 8 November

`plan.reject` (human only, with a reason) moves a proposed plan version to the new terminal state `rejected`: it leaves the attention queue, its planning request records the reason, a `plan.rejected` event is emitted and the coordinator wakes (`plan-resolved`); the confirmed version and its work are untouched. The mission Plan tab's proposal review and the planning canvas both offer Reject. A parked work item's panel offers Retry (back to ready, unparked, failure count reset), Drop (abandoned, after a confirmation), Reassign (another team member) and Edit (title and acceptance criteria); Reassign and Edit propose and confirm a new plan version rather than editing work in place, so the changed task gets a fresh work item. The capitalization browser spec now waits for the clicked run to be queued before processing, removing a request race.

## Plans and runs fold into missions and Logs — 8 November

The fourth UI slice removes `/w/:id/plans` and `/w/:id/runs`, as the #25 route map decided. Planning lives on the mission's Plan tab: its proposal canvas asks Brain for a strategy (or another one), edits each step's outcome, criteria and dependencies, and confirms it — proposing an edited version first — so nothing becomes tracked work before an explicit confirmation; the tab keeps the agent-proposal review, the mission's work items and their scheduled starts. ## Plays absorb tasks, agents and schedules — 8 November

The third UI slice (T58) folds the agent, workflow and schedule pages into Plays, as the #25/#43 route map decided. A declared workflow is a one-task Play: `/w/:id/plays` lists the active release's Plays and single tasks and keeps the guided entry (describe the work, or start from a ticket, incident or work item, reviewed in place), and `/plays/:id` opens either a Play — brief, team roles with each member's agent definition, plan shape, schedules and triggers, the missions it started (`Mission.playId`), and Start into `/w/:id/missions/new` — or a single task, whose typed inputs are reviewed and dispatched there with its schedules and the agents it runs. `plays.get` returns the Play's full spec. The release compiler refuses a Play and a Workflow with the same id. Schedules live on what they start: a Play, a task, or a mission's work items on its Plan tab. Active agent definitions are listed in the Agent Studio for authoring. `/w/:id/agents`, `/w/:id/workflows` and `/w/:id/schedules` are removed without redirects.

## Subjects and mission bundle checks — 8 November

T44 makes tickets and incidents subjects that missions are about: `mission.create` takes subject references that must exist in their pack, missions report their subjects, and `missions.forSubject` lists the missions about one. An automation may use a subject trigger to start a Play for every new ticket or incident; each subject fires an automation once, and newly ingested GitLab tickets fire it. The delivery dossier, its rubric results and the `/w/:id/delivery` screen are removed: evaluators record checks on the mission's current evidence bundle (`recordBundleCheck`), and the advisory judge (`application/bundle-judge.ts`, ADR 0023) records advisory checks with CAS transcripts when a bundle is submitted and the workspace has a hosted model — a recommendation that never records the mission verdict. Moving the Support and SRE queues under Plays belongs to the UI rewrite (T34/T58).

## Attention notifications — 8 November

T65 notifies only on attention items, never on progress. The maintenance pass sends each mission attention item to the mission's starter and to people who chose `mission.watch`, while they still have workspace access, once per item and at most once per mission every 15 minutes; approvals keep their immediate push to approvers. Every notification is recorded in the user's in-app inbox (`notifications.list`) and pushed to subscribed browsers; an optional external channel is not configured yet.

## Attention and since-last-visit — 8 November

T59 adds `attention.list`, derived across the user's workspaces and never stored, in fixed tiers: approvals (nearest expiry first), stopped missions (budget pause, or all remaining work parked), plan proposals and parked work items (with their waiting dependents), verdicts ready to close, and findings routed to a mission; within a tier the longest wait comes first, and no model ranks anything. `missions.sinceLastVisit` returns a deterministic digest of a mission's notable events after the user's seen cursor (work verified, parked work, plan proposals and confirmations, state changes, outputs, brief and budget changes, verdicts) with every other event counted; `mission.seen` advances that cursor per user and mission on the server, so the same news is not repeated on another device, and never moves it backwards. E119 is covered.

## Knowledge from missions — 8 November

T57 runs one capitalization pass when a mission closes, whatever its outcome, and `capitalization.run` accepts a `missionId` for an on-demand pass during a long mission. A mission pass extracts candidates only from verified material: active accepted decisions, verified output versions, mission verdict findings and the Governor-derived facts frozen on handoffs. Member notes, messages and transcripts are never read. Candidates enter the existing review and publication lifecycle as extracted knowledge assets. E120 is covered.

## Event-driven coordinator — 8 November

T66 makes missions advance on events (ADR 0004). A Play may name a coordinator on its team and a coordinator workflow from the same release; the compiler checks that workflow accepts the coordinator input `{ missionId, reasons }`. Mission events record durable wakes — verified work, a message to the mission itself, a plan version a human confirmed, a budget change and a budget pause — and the maintenance pass starts at most one coordinator run per mission, carrying every wake that accumulated, so bursts coalesce into one bounded session. A coordinator start that fails leaves its wakes pending with the error recorded. A mission budget may reserve a final allowance: ordinary work must leave it unspent, while the coordinator may use it, including while the mission is paused for budget, to write the final checkpoint and handoff.

## Scheduled Plays — 8 November

T52 lets an automation target a Play. Each due occurrence starts a mission from the Play on behalf of the person who created the automation (so ownership and notification follow them), records the mission as the occurrence's dispatch reference, and leaves the Play's plan and team as a proposal awaiting human confirmation. The skip overlap policy holds new occurrences while the mission an earlier one started is still open; replays of the same occurrence never start a second mission. The Schedules screen offers "Start a mission from a play" as a target. Triggers from subjects (tickets, incidents) arrive with the Play views in T44.

## Plays — 8 November

T63 adds `Play` as a release kind: title, intent, success criteria, constraints, a team of members naming agent definitions of the same release (and an optional coordinator on that team), a plan template, an autonomy preset, a parking threshold and a budget. The compiler rejects a Play whose team is not mechanically eligible for its plan or whose coordinator is not on its team, so an ineligible Play never activates. `plays.list` / `plays.get` read the active release, and the Studio can draft a Play. `mission.create` with a `playId` copies the Play's brief, budget and parking threshold, clips its autonomy to the workspace ceiling, and proposes the Play's plan and team as a template plan version for human confirmation. `workspace.autonomyCeiling.set` (organization administration only) bounds every mission policy in the workspace; `mission.policy.set` cannot exceed it. Schedules and triggers that start missions from Plays are T52.

## Mission budgets and admission — 8 November

T19 gives missions a budget (spend ceiling, wall-clock ceiling counting only unpaused time, member cap, per-attempt reservation) and puts mission-local admission in front of runner capacity in the claim path. An attempt is admitted only if its reservation fits in budget minus committed spend (settled plus open reservations) and the mission's running work sessions are under its member cap; otherwise the job keeps a waiting reason (`waiting: budget`, `waiting: member cap`, `waiting: runner capacity`, `waiting: mission paused`). Reservations settle from the attempt's reported usage once its runner capacity is released. When nothing fits and nothing runs, the mission auto-pauses with reason budget; `mission.budget.set` (human only) raises the budget and a resume succeeds once there is headroom. Interactive work with no mission is served first, then missions take turns by fewest attempts in flight. E111 and E112 are covered.

## Sessions: one checkpoint, message delivery, context — 8 November

T53 replaces `Checkpoint` and `PortableCheckpoint` with one `brain.checkpoint/v2` shape used by engines and sessions; the Governor stamps the outputs a session consumed and the brief version it worked from, and engine warm-start state (the Pi transcript) travels as `engineState`, never as the source diff. `workItem.message` and its table are removed: mission messages reach a running session live when its engine negotiated steering, at the recipient's next session start otherwise, and Interrupt stops sessions at a safe point instead of cancelling and re-prompting. `sessions.context` returns exactly what a session receives: brief, direct-dependency handoffs, pinned inputs, delivered messages and its last checkpoint. Engine adapters: Pi steers through `session.steer` only while a run streams (#30) and resumes by forking the pinned transcript into the current worktree as a new session (#28, #29); Claude uses streaming input so steering joins the live turn with priority `next` and captures the SDK session id (#31); ACP records the session capabilities the agent advertises and offers nothing beyond what the adapter implements (#32). The live Pi checkpoint/resume probe passed against the local model. E118 is covered.

## Handoffs and mission evidence bundles — 8 November

T62 adds handoffs as evidence artifacts owned by `modules/evidence`. A member submits notes (summary, decisions, open questions, next action, referenced outputs), which stay claims; each submission supersedes the last. At Done the Governor requires a current handoff for work that others depend on, refuses notes that reference outputs the work did not produce as final, and freezes Governor-derived facts (evidence digest, per-criterion status, final output versions, source revision) on the handoff. A dependent reads only its direct dependencies' handoffs (`handoffs.forWorkItem`). Proposing completion assembles a mission evidence bundle; an incomplete bundle returns the mission to work with findings sent to the coordinator as a mission message, and `achieved` requires a verified verdict on the current bundle, which no team agent can record. E116 is covered.
