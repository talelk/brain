# أعراف طلبات السحب (pull request)

هذه هي الإعدادات الافتراضية لمساحة العمل. وتُقدَّم عليها قواعد المشروع نفسه (`CLAUDE.md` و`AGENTS.md` ودليل المساهمة أو قالب pull request) كلما اختلفت عنها.

## pull request واحد، غرض واحد

- يؤدي الـ pull request شيئًا واحدًا: إصلاحًا واحدًا أو ميزة واحدة. وإعادة الهيكلة التي يحتاجها التغيير جزء منه، أما التنظيف الذي لا صلة له به فلا.
- اجعله صغيرًا بما يكفي لمراجعته في جلسة واحدة. وإن زاد الـ diff على نحو 400 سطر معدَّل، فاذكر في الوصف سبب تعذّر تقسيمه.
- لا تُعِد تنسيق أسطر لم يمسّها التغيير، ولا تضف ملفات مولَّدة ما لم يكن المشروع يحفظها في مستودعه.

## العنوان

سطر واحد لا يزيد على 72 حرفًا، يبيّن ما يفعله التغيير ويبدأ بفعل: "رفض الدعوات المنتهية عند تسجيل الدخول". لا "إصلاح خطأ"، ولا رقم الـ issue وحده. واتبع أسلوب البادئات في المشروع (مثل `fix:` أو `feat:`) إذا كان سجلّه يُظهر واحدًا.

## الوصف

بصيغة Markdown، وبهذا الترتيب:

1. **ماذا**: السلوك الذي يتغيّر، في جملتين إلى أربع جمل، بعبارات يفهمها مستخدم الشيفرة.
2. **لماذا**: الـ issue أو الهدف الذي يجيب عنه، مع رابط أو مرجع إن وُجد.
3. **كيف جرى التحقق**: الأوامر التي نُفِّذت بالضبط ونتيجتها، والاختبار الذي أُضيف. ما نُفِّذ فعلًا فقط.
4. **ملاحظات للمراجع**: المخاطر، والقرارات التي كان يمكن أن تذهب في اتجاه آخر، وما تُرك لاحقًا عن قصد.

## ما لا يحتويه pull request أبدًا

- سرًّا أو رمزًا أو كلمة مرور أو بيانات عميل حقيقي، سواء في الشيفرة أو الاختبارات أو بيانات الاختبار أو الوصف.
- اختبارًا مُعطَّلًا أو محذوفًا دون تفسير في الوصف.
- اعتمادية جديدة دون جملة تبيّن سبب الحاجة إليها.
- تغييرات في ملفات التكامل المستمر أو النشر أو الصلاحيات، إلا إذا كان الهدف منها هو ذلك بالضبط.

## كيف تُفتح طلبات السحب هنا

- يترك الوكلاء التغييرات في نسخة العمل. ولا يُجرون commit ولا push ولا دمجًا أبدًا.
- لا يُفتح pull request إلا بالأداة `git.open-pr`، انطلاقًا من diff نسخة العمل، على فرع تسمّيه Brain. ويوافق شخص على الاستدعاء قبل حدوثه.
- لا يدمج أي وكيل شيئًا. بل يدمج شخص بعد أن تنجح فحوص المشروع نفسه.
